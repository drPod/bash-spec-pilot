# Prior-art landscape: LLM-assisted verified code generation and neural theorem proving

Scope: this document maps the systems named in VERINA's related-work table (arXiv:2505.23135, Ye et al., ICLR 2026) plus the neural-theorem-proving lineage that feeds the Lean/Coq/Isabelle side of that table. Every system below was checked against its arXiv abstract, official project page, or publisher record during this survey (July 2026); none are paraphrased from training-data memory. Where a claim could not be confirmed, that is stated explicitly rather than invented.

Anchor paper: VERINA (Verifiable Code Generation Arena), 189 hand-curated Lean tasks spanning code, specification, and proof generation, with modular scoring of each task and their compositions. Best general-purpose model (OpenAI o3): 72.6% code correctness, 52.3% spec soundness-and-completeness, 4.9% proof success in one trial. Best specialized theorem-proving model (Goedel-Prover-V2-32B): 11.2% proof success in one trial. This document exists to place VERINA, and by extension our own Bash-verification project, on the wider map.

It is the closest existing system to "take a real-world, not-designed-for-verification language and get it into a proof assistant," but the translation is a deterministic compiler pass, not an LLM, and Rust already has a memory model clean enough (via its type system) to make the translation tractable. Nothing comparable exists for Bash, whose semantics are defined by an underspecified man page and a reference implementation, not a type system.

## 2. Prose by cluster

### 2.1 Verification-oriented languages (the substrate)

Dafny (Leino, LPAR 2010, LNCS 6355) and Verus (Lattuada et al. 2023) are not code-generation systems; they are the verification-friendly languages that most of the LLM systems below target. Both compile specifications and proof hints (pre/post-conditions, loop invariants, lemma calls) down to verification conditions discharged by an SMT solver (Z3, via Boogie for Dafny, directly for Verus). Crucially, the programmer never writes a proof script in the ITP sense: the SMT solver either closes the goal automatically or fails, and the human's job is only to supply enough hints (assertions, invariants) that it can close the goal. This is what makes Dafny and Verus "ATP" in VERINA's table typology: the theorem proving itself is fully automated once the hints exist, and LLM effort concentrates on supplying those hints or the surrounding code, not on writing multi-step interactive proofs.

### 2.2 Dafny-based LLM systems

Dafny-Synthesis (Misu et al. 2024) is the first empirical study of LLMs writing verified Dafny code end to end, on 178 MBPP-derived problems; retrieval-augmented chain-of-thought prompting took GPT-4 from 19% (bare prompt) to 58% verified. DafnyBench (Loughridge et al. 2025) inverts the setup: take 750+ real, already-correct Dafny programs, strip the verification hints, and see whether an LLM can restore them, isolating pure proof-repair skill from code synthesis. Clover (Sun et al. 2024) is the system VERINA singles out most directly: rather than trusting the verifier's binary pass/fail, Clover cross-checks consistency between the generated code, its docstring, and its formal annotations, and reports a strong filter (up to 87% acceptance of correct instances, zero false positives on adversarial incorrect ones). Along with Dafny-Synthesis, Clover is one of only two prior systems VERINA credits with covering code, spec, and proof generation simultaneously, though both mix spec and proof into a single undifferentiated task rather than scoring them separately the way VERINA does. Laurel (Mugnier et al. 2025) narrows in on the single most common failure point in this pipeline: the SMT solver stalling on a missing intermediate assertion. By locating the stall point from the verifier's own error message and retrieving similar assertions from the same codebase, Laurel recovers the majority of needed hints on a real-world lemma benchmark (DafnyGym).

### 2.3 Rust/Verus LLM systems

AlphaVerus (Aggarwal, Parno, Welleck 2024) addresses a cold-start problem: Verus had fewer than 10 public repositories to train on, so AlphaVerus bootstraps verified Rust by translating programs from a higher-resource source language and refining candidates through a verifier-guided tree search ("Treefinement"), with no human intervention or fine-tuning required to get a LLaMA-3.1-70B model producing verified output. SAFE (Chen et al. 2025) instead builds a self-evolving fine-tuning loop, using the Verus verifier itself as the ground-truth label to distinguish correct from incorrect proofs generated during training; a fine-tuned model reaches 52.52% accuracy on an expert-built benchmark against 14.39% for zero-shot GPT-4o, a roughly 3.6x jump from targeted fine-tuning alone. AutoVerus (Yang et al. 2025) tackles proof generation specifically (code and spec already given), using a three-agent pipeline mirroring how a human proves Rust code (draft, refine, debug against verifier errors); it solves over 90% of a 150-task benchmark, more than half of them in under 30 seconds or 3 LLM calls. This is the single highest success rate anywhere in this landscape, and it comes from the narrowest task (proof only, ATP backend, code and spec already correct).

### 2.4 Spec-generation systems

nl2postcond (Endres et al. 2024) asks whether LLMs can turn natural-language docstrings into formal postconditions without any proof step at all, and finds the resulting postconditions are generally correct and can catch real bugs (64 historical Defects4J bugs). AutoSpec (Wen et al. 2024) and SpecGen (Ma et al. 2025) both target existing, human-written code (C/C++ and Java respectively) and synthesize the missing specification plus the annotations needed for a downstream ATP verifier to check it, validating each candidate against the verifier before accepting it (AutoSpec) or applying a mutation-and-reselect repair pass when the first attempt fails verification (SpecGen, 279/385 programs). Both are explicitly "spec-and-proof from code," not "code from spec": the inverse direction of most of the Dafny/Verus cluster.

### 2.5 ITP proof-generation systems (Isabelle, Coq, Lean)

This cluster shares a task shape distinct from the ATP clusters above: the proof itself is a sequence of interactive tactic applications or a whole proof script, and there is no SMT solver to fall back on for the hard parts. Baldur (First et al. 2023, Isabelle/HOL) pioneered whole-proof generation plus repair (feeding the model its own prior failed attempt and the resulting error), reaching a then-new state of the art of 65.7% on a 6,336-theorem benchmark when combined with the prior tool Thor. Selene (Zhang et al. 2024, Isabelle/HOL) moved the target from a curated theorem library to a real industrial artifact, the seL4 microkernel, and found success drops to 27.06% on that harder, more realistic distribution. Rango (Thompson et al. 2025, Coq) and PALM (Lu et al. 2024, Coq) both lean on retrieval and hybrid symbolic tooling: Rango pulls in similar whole proofs (not just lemmas) from the current project and synthesizes 32.0% of theorems on a new large-scale benchmark (CoqStoq); PALM lets an LLM draft the high-level proof shape and hands low-level tactic repair to CoqHammer, proving 76.6-180.4% more theorems than prior baselines. miniCodeProps (Lohn & Welleck 2024) and CLEVER (Thakur et al. 2025) both move this cluster into Lean specifically and both isolate proof generation as a first-class evaluated task rather than a side effect of code generation. CLEVER, submitted one week apart from VERINA on arXiv, is the closest sibling benchmark to VERINA: both are curated (not test-case-supervised or LLM-annotated), both hold out ground-truth specs, and both report current methods "struggle to achieve full verification" without a strong headline number.

### 2.6 Specialized LLM provers

Where the systems in §2.5 mostly repurpose general-purpose LLMs, this cluster trains models specifically for formal proof search. Goedel-Prover-V2 (Lin et al. 2025) and DeepSeek-Prover-V2 (Ren et al. 2025) are the two current open-source frontier provers for Lean 4, both trained via expert iteration / reinforcement learning with verifier feedback baked into training rather than only used at inference. Goedel-Prover-V2-32B reaches 88.1% pass@32 on MiniF2F and leads open models on PutnamBench (86/657 problems); DeepSeek-Prover-V2-671B reaches 88.9% on MiniF2F-test. Both numbers come from math-competition benchmarks (MiniF2F, PutnamBench), not from verifying arbitrary software; when the same model family (Goedel-Prover-V2-32B, and a 7B DeepSeek-Prover-V2 variant) is dropped into VERINA's software-verification proof task, performance collapses to 11.2% and below, respectively. This is the single most important number in this whole survey for calibrating "SOTA prover" against "SOTA prover on code correctness proofs." Copra (Thakur et al. 2023) takes a different approach, wrapping a general-purpose GPT-4 in a stateful tree-search agent that incorporates verifier feedback and retrieved lemmas turn by turn; it improves on few-shot GPT-4 but, when re-evaluated inside VERINA at matched token budgets, is beaten by plain iterative refinement (7.94% vs 14.29% at 350K tokens). LeanDojo (Yang et al. 2023) and Lean Copilot (Song, Yang, Anandkumar 2024) are infrastructure rather than end-to-end provers: LeanDojo opened up programmatic Lean interaction and premise retrieval that much of this later work depends on, and Lean Copilot runs LLM inference natively inside the Lean editor, automating 74.2% of proof steps unattended and roughly halving the steps a human has to type by hand. Kaiyu Yang, LeanDojo's lead author, is also a VERINA co-author, a direct lineage link between the infrastructure and the benchmark.

### 2.7 Real-world deployment

AWS Cedar (Cutler et al. 2024) is the outlier in this table: it is not an LLM-generation result at all. Cedar's authorization-policy semantics were modeled by hand in Lean, and Amazon's engineers hand-proved properties like "forbid trumps permit" and "default deny," then checked the hand-formalized model against the production Rust implementation by differential random testing. The process found and fixed 4 bugs via the proofs themselves and 21 more via the resulting differential/property-based testing. Cedar matters to this landscape not because it involves LLMs, but because it is the strongest evidence available that Lean-based formal verification survives contact with a real, shipping, security-critical system: it answers "is this backend viable in production" independently of whether LLMs can drive it.

## 3. The through-line: how automatable is a machine-checked correctness proof, today

The systems above split cleanly by proving style, and the gap between the two styles is the central empirical fact of this landscape.

**ATP (Dafny/Verus, SMT-backed).** Once code and specification exist, filling in the SMT solver's remaining hints is comparatively tractable:
- AutoVerus (proof only, code+spec given, curated 150-task benchmark): 90%+ solved.
- Dafny-Synthesis (full code+spec+proof pipeline, MBPP-level difficulty, 178 problems): 58% with a well-engineered prompt.
- SAFE (proof only, Rust/Verus, expert benchmark): 52.52% after self-evolved fine-tuning, versus 14.39% zero-shot.
- Laurel (single-assertion repair, real-world lemmas): 56.6%+.
- Clover (consistency-filter acceptance rate on correct Dafny instances): up to 87%.

**ITP (Lean, Coq, Isabelle, no SMT fallback).** The same class of task, on code-correctness rather than pure-math theorems, is dramatically harder:
- VERINA, best general-purpose LLM (OpenAI o3), pass@1: 4.9%.
- VERINA, best specialized Lean prover (Goedel-Prover-V2-32B), pass@1: 11.2%.
- VERINA, iterative refinement with up to 64 rounds of Lean-compiler feedback: rises to about 20.1% in aggregate, but cost grows sharply and proof text balloons (human ground-truth proofs average 169.6 characters; the same model's 64-iteration refined proofs exceed 1,200 characters) without matching human concision.
- VERINA's harder subset (VERINA-B) barely moves under refinement: o4-mini goes from 1.23% to just 6.17% after 64 iterations, versus 7.41% to 22.22% on the easier subset (VERINA-A).
- Baldur, on pure Isabelle/HOL math theorems (not software correctness): 65.7% combined with prior SOTA, showing ITP proof generation is *not* uniformly hard, but is hard specifically on code-correctness goals, which tend to require more domain-specific lemma use than competition-style math.
- Selene, on the seL4 microkernel (real industrial Isabelle artifact): 27.06% best average.
- Rango, on a large real-world Coq corpus: 32.0%.
- Frontier math provers (Goedel-Prover-V2, DeepSeek-Prover-V2) clear 84-90% pass@32 on MiniF2F and PutnamBench, math-competition benchmarks, but the same model families drop to single-digit/low-double-digit percentages on VERINA's software proofs.

The pattern holds across every ITP entry that touches software (as opposed to pure math): proof success rates sit roughly 5-10x lower than the equivalent ATP task, and the gap is not closed by more inference-time compute (iterative refinement, agentic tree search): it narrows but does not close, and the extra compute buys diminishing, verbosity-inflating returns. VERINA's own framing (§2, background and related work) makes the tradeoff explicit: SMT solvers are more automatable today but are "black boxes" that produce "brittle and hard to debug" proofs, whereas ITP systems expose intermediate proof steps that let an LLM diagnose its own errors and improve iteratively over time, at the cost of much lower current success rates. That is a bet on where the field is going, not a claim about where it is now.

## 4. The gap for our project

Every system surveyed above verifies a program written **in** a verification-friendly language: Dafny, Rust annotated with Verus specs, or Lean/Coq/Isabelle directly. In every case, either (a) the program's semantics are already machine-checkable by construction (Dafny and Verus are designed so that an SMT solver can decide most verification conditions automatically), or (b) the program already lives inside the proof assistant as executable Lean/Coq code (miniCodeProps, CLEVER, VERINA itself). The one partial exception, Aeneas (Ho & Protzenko 2022), translates a real-world systems language (Rust) into a Lean/F*/Coq-checkable functional model, but that translation is a deterministic compiler pass exploiting Rust's own type system to eliminate memory reasoning, not an LLM-driven or heuristic embedding of an underspecified language's semantics.

None of these systems verifies a program written in a **foreign** language whose semantics are not already machine-checkable and must first be embedded or modeled. That is precisely our project's situation: Bash and the GNU coreutils it invokes have no type system, no formal semantics, and a specification (the man page) that is prose, incomplete, and sometimes wrong relative to both POSIX and the actual binary (per this repo's own man-page-defect findings). Getting from "real Bash utility behavior" to "a claim a proof assistant can check" requires building the semantic bridge itself, a step every system in this survey gets for free by construction or by targeting an already-formal language.

This has a direct, practical implication for backend choice. VERINA's headline number, an 11.2% best-case proof success rate for a specialized Lean prover on software-correctness goals (4.9% for general-purpose LLMs), describes the ceiling on today's ITP automation even when the target language (Lean) is the friendliest possible case: no foreign-language embedding problem, clean functional semantics, an active research community optimizing provers against exactly this benchmark. If our Bash-verification pipeline also had to route through raw Lean ITP, we would be composing that low a success rate with an additional, harder, largely unsolved translation step (Bash-to-formal-model), compounding two hard problems where VERINA only has one.

Dafny- or Verus-style ATP is a more practical backend candidate for exactly the reason VERINA gives for avoiding it: SMT-backed verification is a black box, but it is a black box with a 50-90% close rate on the kinds of hint-completion and small-function verification tasks this survey documents, roughly 5-10x higher than the equivalent ITP proof-generation numbers. If the Bash-to-formal-model translation step (the part with no existing prior art) can be designed to emit Dafny- or Verus-style specifications with SMT-checkable proof obligations, rather than Lean tactic proofs, the LLM-facing proof-generation task inherits ATP's much higher current automation rate instead of ITP's single-digit one. The tradeoff, per VERINA's own argument, is long-term: ATP proofs are harder to debug and their failures are less diagnosable by an LLM than ITP's step-by-step structure, which may matter more once the harder translation problem is solved and proof generation itself becomes the bottleneck rather than the embedding. For now, given where the numbers actually are, an SMT/ATP-backed target looks like the more tractable near-term choice for a project that already has to solve the embedding problem no one else in this survey had to solve.
